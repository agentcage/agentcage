# Distribution packaging

agentcage ships as a single static binary. The release workflow builds
four of them and attaches each to the GitHub release with a `.sha256`
beside it:

| Platform | Asset |
| :-- | :-- |
| Linux x86-64 | `agentcage-<version>-x86_64-unknown-linux-musl.tar.gz` |
| Linux arm64 | `agentcage-<version>-aarch64-unknown-linux-musl.tar.gz` |
| macOS Apple Silicon | `agentcage-<version>-aarch64-apple-darwin.tar.gz` |
| macOS Intel | `agentcage-<version>-x86_64-apple-darwin.tar.gz` |

Everything downstream reads those assets: `install.sh`, the Homebrew
formula and the AUR `PKGBUILD`.

## Why these are templates

A Homebrew formula and a `PKGBUILD` both pin a version *and* a checksum,
so both are wrong the moment a release ships and right again only when
someone regenerates them. Hand-editing four checksums per release is how
a tap ends up installing the previous version, so neither file is
committed in a filled-in state — `scripts/gen-packaging.py` produces
them from a release's published checksums:

```sh
# From the assets a release workflow just built:
python3 scripts/gen-packaging.py --version 0.41.0 --dist ./dist

# Or straight from a published GitHub release:
python3 scripts/gen-packaging.py --version 0.41.0 --from-release
```

It writes `agentcage.rb` and `PKGBUILD` into the output directory, ready
to commit to the tap repository and the AUR package respectively.

## The two repositories

Neither lives here, because neither can:

* **Homebrew tap** — `homebrew-agentcage`, a separate GitHub repository
  Homebrew clones. `brew install agentcage/agentcage/agentcage`.
* **AUR** — `agentcage-bin`, a git repository on aur.archlinux.org with
  its own `.SRCINFO`, regenerated by `makepkg --printsrcinfo`.

Until those exist, `install.sh` and a manual download are the install
paths, and both are documented in `docs/get-started/install.md`.
